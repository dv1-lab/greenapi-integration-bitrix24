# Architecture Decision Records (ADR)

Каждый файл — одно **продуктовое или техническое решение** с
обоснованием. Чтобы через год/полгода/в следующей сессии можно было
понять «а почему так?» — а не разводить дебаты с нуля.

## Формат файла

```
# YYYY-MM-DD — <короткое название>

## Контекст
Что было, какая проблема, что заставило принимать решение.

## Решение
Что выбрали из вариантов.

## Альтернативы
Что рассматривали и почему отвергли.

## Последствия
- что улучшилось
- что усложнилось
- что нужно мониторить

## Связано
- ссылки на code (sha), memory, PRODUCT_RULES.md секции
```

## Когда писать ADR

- Изменение настроек внешней системы (B24, Green API, i2crm)
- Выбор архитектурного подхода (polling vs webhook, sync vs async)
- Бизнес-правило которое раньше было устным
- Откат / переключение между вариантами
- Любое решение которое в будущем может вызвать «а почему?»

## Когда НЕ писать ADR

- Очевидный bug-fix (это в REGRESSIONS)
- Косметика кода
- Внутренняя рефакторинг без поведенческих изменений
