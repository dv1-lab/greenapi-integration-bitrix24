# ADR 2026-05-26: QUEUE_TYPE=evenly + CRM_TRANSFER_CHANGE=N для всех open-lines

## Контекст

Анастасия Василенко зафиксировала в task-tracker задачу **#55**:
«надо чтобы лиды распределялись на всех, кто в смене».

Сценарий-триггер (raf._mus, лид [#359250](https://1begovoy.bitrix24.ru/crm/lead/details/359250/)):

- Клиент писал в IG Direct раньше, Анна Коваленко закрыла диалог в 16:09
- В 17:19 клиент написал снова → создан **новый лид #359250**
- Лид **автоматически направлен на Коваленко Анну** «как ответственного в CRM»
- Анастасия Василенко вынуждена была вручную взять диалог в 17:45

Проблема: B24 OpenLines при повторной сессии **сохраняет ответственного**
из предыдущего лида, игнорируя то что у этого оператора может быть
неудобное время или она вообще не в смене.

## Корень — два параметра B24

| Параметр | Текущее значение | Поведение |
|---|---|---|
| `QUEUE_TYPE` | `all` | Уведомление приходит **всем 6 операторам сразу**. Первый кто откликнется — берёт |
| `CRM_TRANSFER_CHANGE` | `Y` | При повторной сессии в открытой линии — **назначается ответственный** из предыдущего лида |

Оба фактора суммарно дают «лид прилетел на того же кто был ответственным
раньше, а не на текущую смену».

## Решение

Применить на **все 14 активных open-lines** портала:

```
PARAMS[QUEUE_TYPE]              = evenly   # round-robin между операторами
PARAMS[CRM_TRANSFER_CHANGE]     = N        # новая сессия → новый ответственный по очереди
```

Возможные значения `QUEUE_TYPE` в B24:
- `all` — всем сразу (было)
- `evenly` — равномерно по очереди (round-robin) ← **выбрали**
- `strictly` — строгая очередь (по приоритету в списке)

## Кого распределяет

Очередь линии (`QUEUE` параметр) содержит user_id операторов. Для линии 18
(IG Direct):

```
21370, 3752, 67838, 110528, 119176, 124484
```

`evenly` идёт по этому списку round-robin. **Не сменам** в строгом
понимании рабочего расписания — Битрикс не знает кто сейчас «в смене», он
просто чередует. Если оператор offline в B24 — пропускается, следующий по
очереди.

> **Гипотеза от support B24**: ‘evenly’ + статус оператора (online/offline)
> = эквивалент «smen-aware» round-robin. Не подтверждено эмпирически, но
> по логике должно работать так.

## Применено через `imopenlines.config.update`

Команда (через adapter accessToken):

```bash
curl -G "https://1begovoy.bitrix24.ru/rest/imopenlines.config.update" \
    --data-urlencode "auth=$TOKEN" \
    --data-urlencode "CONFIG_ID=<line>" \
    --data-urlencode "PARAMS[QUEUE_TYPE]=evenly" \
    --data-urlencode "PARAMS[CRM_TRANSFER_CHANGE]=N"
```

Применено к линиям: **4, 8, 18, 22, 110, 148, 174, 178, 180, 182, 184,
186, 204, 206** (все active=Y).

## Что НЕ менялось

`CRM_FORWARD=Y` оставлен — это правильно: если у клиента есть **открытая
сделка**, новая сессия идёт в неё (а не создаётся новый лид). Это
совместимо с задачей #66 (привязка к открытой сущности).

`CRM_CREATE=lead` оставлен — новые клиенты создают лид через open-line,
как раньше.

## Verify

После изменения:
- Новый клиент пишет в WA/TG/IG → лид создаётся, **направляется
  следующему по очереди оператору** (round-robin)
- Existing клиент с открытой сделкой → forward в сделку (unchanged)
- Existing клиент **без** открытых сущностей → новый лид, но
  ответственный **не сохраняется** из предыдущего лида, идёт round-robin

Проверка на новом обращении (через час-два после деплоя): должен быть
другой ответственный, не та же Коваленко Анна.

## Если что-то пошло не так

Откат на старое поведение через тот же endpoint:
```
PARAMS[QUEUE_TYPE]=all
PARAMS[CRM_TRANSFER_CHANGE]=Y
```

Но это вернёт к проблеме «лид на ответственного из прошлого лида».
